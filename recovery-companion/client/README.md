The PC client requires Node 18 or newer. Keep its JSON configuration and RSA private key outside the repository. The companion widget contains the matching public key and a separate server TLS credential; the PC private key is never packaged.

Client configuration fields are `host`, `port` (8098), `certificateSha256` (SHA-256 of the TLS leaf certificate DER bytes, lowercase hex), and `privateKeyPath` (absolute local PEM path). Provision the certificate pin through a trusted local channel. The client verifies this pin before sending HTTP headers or widget bytes.

To explicitly select **PC native remote mode**, add private `tvRemoteToken`, optional matching `tvRemoteName` (default `HomeAssistant`), and required `tvRemoteCertificateSha256` (SHA-256 of the TV native port 8002 leaf certificate DER, lowercase hex) to that PC configuration. `remote` then connects directly from the PC to the configured TV host on port 8002, with the native certificate pin verified before sending the token-bearing WebSocket request. It does not contact or start the companion, so remote keys remain usable while the companion is stopped. Without these optional fields, `remote` uses the authenticated companion service route. This mode selection is explicit; errors never cause automatic switching between the two paths. Native PC credentials stay outside the repository and widget. Native mode results identify `source: "pc-native"`; neither mode confirms an OS reboot merely because a power key was delivered.

```powershell
node recovery-companion/client/cli.cjs --config C:/Users/neoya/share/recovery-client.json start
node recovery-companion/client/cli.cjs --config C:/Users/neoya/share/recovery-client.json status
node recovery-companion/client/cli.cjs --config C:/Users/neoya/share/recovery-client.json capabilities
node recovery-companion/client/cli.cjs --config C:/Users/neoya/share/recovery-client.json remote KEY_HOME
node recovery-companion/client/cli.cjs --config C:/Users/neoya/share/recovery-client.json remote KEY_POWER --hold-ms 5000

node recovery-companion/client/cli.cjs --config C:/Users/neoya/share/recovery-client.json install C:/path/TizenBrew-signed.wgt
```

`start` explicitly requests the fixed companion application through the configured TV's native HTTP port 8001, with a three-second deadline. It then polls authenticated, pinned TLS status for up to twenty seconds. A native launch acknowledgment alone does not prove service readiness. No other command starts the app automatically, and a certificate pin or authentication failure never triggers fallback launching. Reboot recovery through this command requires the TV's native application REST endpoint and companion foreground bootstrap to work on that firmware; hardware verification is still required.

`capabilities` authenticates before reporting the installed service's implemented routes, current Node process runtime and numeric UID/GID, OS uptime, and a SHA-256 digest of the kernel boot ID. Identity is `null` where unavailable; it reflects this process rather than assuming the SDB daemon's permissions. It reads at most 128 bytes from a fixed kernel path and never returns the raw boot ID. Missing or inaccessible boot metadata is `null`. Compare the digest and uptime before and after a separately performed restart; a changed app session or standby/wake alone does not establish a full OS reboot. The runtime's `platform` is the Node host OS (for example Linux), not the TV's Tizen product version.

The authenticated `framebufferAccess` record separately checks three fixed, small framebuffer metadata files and whether this service can open `/dev/fb0` read-only and nonblocking. It immediately closes that descriptor without reading any pixels. This distinguishes service filesystem access from the SDB file-transfer whitelist; successful opening alone does not establish a usable full-TV image or video/OSD coverage.

Full-TV screen capture and full OS reboot are reported as unavailable and unverified because this service has no verified backend for them under its current permissions. This reports the installed implementation's limits, rather than asserting that every firmware lacks these features. CDP capture covers one app document and cannot be presented as the complete TV display. Samsung's documented [`captureScreen` and `rebootDevice`](https://developer.samsung.com/smarttv/develop/api-references/samsung-product-api-references/systemcontrol-api.html?device=signage) require its B2B SystemControl API and Partner privilege. Remote power keys or standby are separate operations. No full-screen capture, OS reboot, or arbitrary shell HTTP endpoint is enabled.

`remote` sends an allowlisted key through the TV's native TLS WebSocket on fixed port 8002. The target defaults to `127.0.0.1`; optional private `tvRemoteHost` is accepted only if it matches this service's own noninternal IPv4 address, rechecked before each command. Hostnames and arbitrary remote targets are rejected. Authenticated runtime capabilities include these local IPv4 addresses without interface names or MAC addresses. The companion's private configuration must contain a previously authorized `tvRemoteToken` and may specify the matching plain `tvRemoteName` (default `HomeAssistant`). Credentials are not returned in status/capabilities or copied to the PC configuration. Missing credentials disable the route; refused authorization fails without silent pairing or reconnecting. Native TV permission may depend on the source address, so reusing an existing remote profile does not guarantee authorization from loopback. Authenticated failures expose allowlisted transport codes such as `ECONNREFUSED` or `HTTP_403` and at most 256 characters of diagnostic detail. Tokens, URLs, control characters and stack traces are removed from that detail.

Keys are `KEY_HOME`, `KEY_RETURN`, `KEY_EXIT`, `KEY_MENU`, `KEY_UP`, `KEY_DOWN`, `KEY_LEFT`, `KEY_RIGHT`, `KEY_ENTER`, `KEY_0` through `KEY_9`, `KEY_POWER`, `KEY_MUTE`, `KEY_VOLUP`, `KEY_VOLDOWN`, `KEY_PLAY`, `KEY_PAUSE`, and `KEY_STOP`. Default behavior is Click. `--hold-ms` accepts an integer from 500 through 10000 and sends Press followed by Release. One command runs at a time, with a 15-second absolute native transport deadline. Every terminal path after a possible Press attempts Release on the same live connection; if the connection fails, delivery cannot be guaranteed and the operation fails. A short graceful close window lets sent packets drain. A successful response confirms transport delivery, not the observed TV effect. `KEY_POWER` is blocked during uploads, installation, or an inconclusive update, and a pending power command blocks installation. A power hold is not advertised as an OS reboot.

The tunnel binds only to PC loopback. Port `0` chooses an available local port; the client prints that actual port for `sdb connect`. Each authenticated connection forwards raw TCP only to the TV's `127.0.0.1:26101`, with a five-minute lifetime, thirty-second idle timeout, and two-connection limit. An authorized key holder receives full SDB capabilities through this tunnel; it is not a restricted shell or a package-policy firewall. Use SDB forwarding for a debug port when needed; there is no separate CDP endpoint.

The upload endpoint additionally verifies a signature over the complete widget bytes and permits only package `xvvl3S1bvH`, application `xvvl3S1bvH.TizenBrewStandalone`. It rejects the companion package. Uploads are staged with exclusive creation and mode 0600, then installed through a fixed localhost SDB command. Check authenticated status for completion. An inconclusive result blocks another installer attempt until the companion is restarted, because the OS installer might still be running.

Challenges expire after thirty seconds and are single-use. Signatures bind the nonce, exact method and path, declared byte count, and SHA-256 body digest. Status and installer logs require authentication. The independent companion must have been launched and must still be running; it cannot promise availability after the TV kills its service or reboots.

The separate PC command `capture-app.cjs` saves a PNG of the existing TizenBrew app document. Supply its currently active debug port; this command does not discover ports, launch an app, navigate, attach a new TV debugger, or restart the existing debug session.

```powershell
node recovery-companion/client/capture-app.cjs --config C:/Users/neoya/share/recovery-client.json --sdb C:/path/to/sdb.exe --port 39415 --out C:/Users/neoya/share/tizenbrew-app.png
```

All three paths must be absolute. The debug port must be an integer from 32768 through 65535. The PNG output must not already exist. The command opens an authenticated, pinned recovery SDB tunnel, connects SDB to its ephemeral PC loopback port, and creates a temporary forward to the supplied TV debug port. It reads the forwarded CDP `/json/list` response with a three-second deadline and 256 KiB limit. A target must return the exact application ID `xvvl3S1bvH.TizenBrewStandalone` through `Runtime.evaluate` before `Page.captureScreenshot` is sent. Target names and URLs alone never authorize capture. Unavailable Tizen identity APIs, a paused page that cannot answer, or unsupported screenshot methods fail without trying another capture mechanism. The PNG is limited to 8 MiB and created exclusively. Cleanup removes only the command's own forward and SDB transport, then closes its CDP connection and local tunnel; it does not terminate the existing app debugger.

This is an **app-document screenshot**, not a full-TV screen capture. It excludes TV Home, native overlays, and other apps; separately composited video planes may also be absent. Hardware support and the actual captured content must be checked on the TV. The command never wakes or foregrounds a hidden app to obtain pixels.
